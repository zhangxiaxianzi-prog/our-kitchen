# 三餐日历需求与方案

## 已确认规则

用户确认以微信小程序为唯一入口，删除网站源码及构建、发布代码，旧网站数据不再迁移。保留微信后台已有厨房与评分，不连接旧网站进行数据删除。

“三餐日历”是独立栏目，不区分早餐、午餐和晚餐。月历支持切换月份、回到今天、点击日期查看菜品；有记录的日期显示圆点。同一天保留多轮，最新一轮在前。

每道菜只有完成双人评分后才进入日历。只完成一个人的评分、不论分数多高，都不显示；一轮没有任何完整评分菜品时也不显示。达到7分的菜直接显示，低于7分的菜放在可展开的淘汰记录中。“再吃这一顿”按钮和前端操作已取消，旧版本调用复用接口时返回中文更新提示，不创建新轮。

日期沿用本轮开始搭配时保存的北京时间日期，不因另一人隔天评分而移动。记录的是选菜和评分，不证明实际已经做过或吃过。

## 手机操作

1. 点击底部“三餐日历”，选择月份和日期。
2. 日期下方按轮次显示历史菜名、主要食材、荤素分类、两人评分和合计分。
3. 每页最多40道菜；上一页、下一页替换当前内容，不无限追加到手机内存。轮次可以跨页，因此卡片明确显示“本页”道数。
4. 点击“查看淘汰菜”展开当前页对应轮次的低分菜。
5. 空日期显示暂无完成双人评分记录；加载失败有独立重试，不清空冰箱。
6. 无法识别日期的旧记录从月历下方单独入口查看，不伪造日期。

页面请求带本次查看编号，切月份、切日期、切栏目、进入后台或退出登录后，迟到响应不会覆盖新页面。厨房定时同步不会每8秒强制跳回日历第一页；同一版本不重查历史，数据有更新时保持正在查看的日期和页码。

## 长期保存

新增 `kitchen_calendar` 独立历史表，每行保存一道已完成双人评分的菜；保存当时菜名、食材和最终分数。厨房仍保留最近30轮操作数据，日历不受这30轮上限影响。新一轮、手动换菜、编辑或删除菜单，不删除归档记录。

通过 `kitchen_calendar_imports` 记录每个厨房是否已补入现存旧记录。首次登录或日历读取时，在事务中补入微信数据库仍保留的完整评分记录，之后不反复搬运。此前已被30轮上限移除的记录无法恢复；用户取消网站后，也不会从旧网站导入记录。

老淘汰记录可能没有主要食材，此时显示“旧记录未保存食材”，不使用当前菜单猜测。新淘汰记录保存完整食材。

评分与历史在同一数据库连接、同一个事务中提交：任何一步失败都回退本次写入。先保存带版本条件的厨房，再保存历史，所有实例采用相同顺序；版本冲突重新读取并合并自己的操作。归档键由轮次编号及候选编号生成，重复请求和重复补入不会新增重复菜品。历史写入后不允许覆盖原分数。

查询都限定当前票据所属厨房，不接受前端指定厨房编号。月份只返回日期和道数；详情每页40道，备份每批100道，恢复每批20道。SQL只操作单表，不使用连表查询；日期、轮次与排序均有对应索引。

长期保存意味着不按业务轮数定期删记录，仍需要数据库备份和正常容量维护，不宣称云数据库永远不会丢失数据。

## 接口

| 接口 | 用途 |
| --- | --- |
| GET /api/calendar?month=2026-10 | 查询月份日期标记和无法识别日期的旧记录数量 |
| GET /api/calendar?date=2026-10-10 | 查询当天第一批最多40道完整评分菜品 |
| GET /api/calendar?date=unknown | 查询日期无法识别的旧记录 |
| GET /api/calendar?date=日期&cursor=上一页返回位置 | 继续查询日期详情 |
| GET /api/calendar/export | 逐批导出长期历史，固定本次截止编号 |
| POST /api/calendar/restore | 每批最多20道追加恢复历史，已有不同内容时整批拒绝 |

备份和恢复只允许读取或追加自己厨房的记录，不返回密码、共同口令或数据库配置。普通厨房备份继续兼容原格式，仅包含菜单、冰箱、采购清单与最近30轮；它不是完整长期日历备份。

## 备份操作

在 `wechat-gateway` 目录执行，口令在终端提示后输入，不放在命令参数中：

```sh
node tools/厨房备份迁移.cjs 导出 /自己的路径/厨房.厨房备份.json
node tools/日历历史备份.cjs 导出 /自己的路径/历史.日历备份.jsonl
node tools/日历历史备份.cjs 导入 /自己的路径/历史.日历备份.jsonl
```

完整备份需要保存厨房文件和日历文件两份。日历文件按行写入，文件存在时不覆盖；必须有完整结束标记和正确道数才可恢复。导出期间新完成的菜属于下一次备份。恢复仅追加：重复记录不新增，已有同一菜品编号但不同日期或分数时拒绝当前批次，不改写原内容。不同批次不组成一个大事务，后续失败时前面成功的批次保留，修复后重试会去重。恢复到另一份厨房时仍需输入目标厨房的共同口令。
