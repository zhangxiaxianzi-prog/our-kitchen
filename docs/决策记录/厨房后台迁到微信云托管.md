# 厨房后台迁到微信云托管

## 背景和已确认决定

2026年10月9日，springboot-5wzu-004调用Sites的登录接口收到403 HTML。日志识别到Cloudflare浏览器验证页。原先让云托管转发Sites接口的设计无法完成该次登录。具体触发哪条安全规则仍无法确认。

用户确认：厨房接口和共享记录迁到现有微信云托管与MySQL，网站保留界面，两个入口最终访问同一后台。先验证新后台，再迁移实际记录，最后切换网站。不使用浏览器验证绕过方式，不维护两套各自可写的数据。

## 比较过的选择

- 在原平台配置受支持的服务访问：改动小，但Sites工具现在返回项目找不到，无法验证这种访问是否可配置。
- 分别给网站和小程序建后台：会让评分和食材不一致，不满足共享要求。
- 微信统一后台：现有云托管和MySQL可用于实现；小程序直接调用，网站通过受限来源的HTTPS接口调用。增加了数据库配置、备份导入和网站切换步骤。

选择第三项。此前共用数据文档记录的是原方案，本记录说明原方案前提被实际云端证据否定后的变更。

## 实现约束

- 共用规则放在wechat-gateway/domain，原lib文件只转出这些规则，不另写两套评分和配菜。
- Node服务分为请求接收、厨房读写顺序、数据库保存、登录票据四部分。复用mysql2连接池和参数化语句、Zod检查备份格式、Node签名能力。
- MySQL 5.7，只用单表SQL。新增kitchen_records和kitchen_login_attempts，不删除模板业务表。
- 保存时要求数据库版本仍等于本次读取版本；冲突最多重读8次。每次只修改自己的评分。换菜轮换候选编号，迟到评分不能打到新菜上。
- 每实例最多5个数据库连接、20个连接等待请求、10个正在处理的HTTP请求。每实例同时只导入一个备份，普通修改8KB、登录2KB、备份4MB、厨房内容2MB。菜单400道、冰箱和采购各200项、历史30轮的原有限制继续保留。
- 30天签名票据，口令原文不落库。新密钥必须固定，所有实例一致。新密钥与原Sites密钥不一致时，重新登录并用备份迁移记录，不能直接搬原厨房编号。
- 登录次数在共享数据库领取：同口令每15分钟20次，全服务每15分钟200次。全服务上限用于限制不断更换口令建空厨房的请求；它也意味着达到上限后其他用户需要稍后重试。

## 数据迁移和回退

先停止两边修改，导出旧厨房并验证结构，导入新建且没有操作过的厨房，再逐项核对内容。导入保存和普通修改共用版本条件，重复导入同一文件不会回退后来的修改。已经使用过的厨房不能被另一个备份覆盖。

原Sites数据库和接口保留。网站开关默认关闭；新后台验证和实际导入之前不启用。切换后禁止在旧后台继续改数据。如果新后台已经产生新记录，回退前必须保存这些记录，不能直接切回旧数据而宣称数据没丢。
