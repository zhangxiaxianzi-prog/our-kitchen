# 双人使用流程完善说明

## 加入申请

申请人首次填写1到20个字符的称呼，提交成功后随微信账号保存，下次自动带出；发送前可修改。称呼不代表微信身份，也不用于判断权限。创建者看到申请当时填写的称呼和账号标识；旧申请显示“旧申请未填写称呼”。旧版客户端不传称呼时仍能申请。

申请人有独立的“我的加入申请”列表，显示等待同意、已通过或已拒绝，每页最多20条。使用申请编号尾部6位辅助区分，审批之前不公开厨房名称或内容；编号不是登录凭证。通过后从厨房列表进入。页面可见时沿用8秒刷新，离开页面停止，旧请求不覆盖另一账号的页面。

拒绝后用户主动点击重新申请，填写有效口令并发送，不自动重申。口令轮换后不能凭旧申请编号再次加入。相同账号对同一厨房只有一条当前申请记录，重申把已拒绝状态改为等待，本次不增加完整申请操作历史。原频率限制和创建者审批保持不变。

本人创建的厨房显示待处理申请数量，仅查询当前页最多20个厨房，使用一次单表分组查询。非创建者不获取待处理数量。此处不使用SQL连表查询或显式行锁。

## 本轮菜单汇总

候选菜上方显示“这顿吃这些”。只汇总双人评分已完成且合计至少7分的菜；显示已选齐或还差几道。缺少食材从这些入选菜合并去重，再扣除当前冰箱记录；不使用对方未公开的分数猜测结果。采购按钮沿用已有接口，可以先为部分入选菜生成清单，不改变清单的追加规则。

重新搭配确认明确说明：已完成双人评分的记录保留在三餐日历，未完成评分的候选会被替换。日历仍记录选菜结果，不证明已经烹饪或吃过。

## 数据库升级及部署

后台启动先检测字段和索引是否存在，只补充缺少的结构。kitchen_accounts与kitchen_join_requests增加nickname字段，申请表增加申请人分页及待处理查询索引；不删除旧记录。多实例同时升级出现重复字段或索引时继续，其他数据库错误停止启动，不当成已成功升级。

本次MySQL5.7改表和建索引可能影响正在访问这些表的请求，需在低峰发布并观察。数据库账号需要对应改表权限。先发布后台，确认字段升级和新GET /api/account/applications接口可用，再上传小程序。既有POST /api/account/join增加可选nickname字段，profile增加称呼，厨房列表增加pendingCount，创建者申请列表增加称呼。
