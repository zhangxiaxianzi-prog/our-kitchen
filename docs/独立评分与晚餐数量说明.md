# 独立评分与晚餐数量说明

## 已确认的使用方式

### 评分与结果

每道候选菜由两个人分别给0～5分。评分期间只显示自己的分数，对方只显示“已评分，暂不公开”或“未评分”。两人都完成这道菜的评分后，公开双方分数和合计，不必等待整顿晚餐完成。出结果后锁定分数，想重新选择可以换菜，新候选重新评分。

合计大于等于7分入选；小于7分时，后台保留本轮淘汰记录，然后随机换一道同类菜，换候选编号并清空两人评分。荤菜换荤菜，素菜换素菜，不与其他候选重复，也不再推荐本轮淘汰菜。自选同样排除本轮淘汰菜。新一轮允许这些菜重新参加推荐，不改变菜单的启用状态。

没有其他合适菜时，保留这道菜的分数和说明，不用重复菜凑数，也不丢掉评分。补充菜单或食材后可以手动“换一道”继续。为防止反复增删菜单使历史无限增长，一轮最多保留400道淘汰结果，到达后保留最后结果并提示开始新一轮。厨房仍沿用最多30轮历史和2MB记录限制。

共同口令仍可选择或切换身份，因此不能防止用户切换身份查看另一个人的自己的分数。这次解决的是正常评分时互相影响，不增加身份认证。

### 每顿吃几个菜

分别选择荤菜、素菜数量，每项可选0～6道，合计需为1～6道。默认一荤两素，也可以全素或全荤。点击开始搭配时，后台按本次数量和食材限制生成候选。数量选择随厨房保存，下次默认沿用最近成功开始的一轮的荤素数量。

开始之后，本轮数量和“只用冰箱已有食材”的选择固定。后续调整用于下一轮，不删除当前已评分候选。只用冰箱模式继续使用当前共享冰箱中的实际食材判断是否齐全，所以补充食材后可继续换菜。菜单不足或数量非法时保留原晚餐，不生成半份候选。

### 冰箱左滑移除

普通查看时，左滑某一条食材露出该条的“移除”按钮，食材名称仍可见。一次只露出一条，右滑、点食材、切换分类或页面会收起。点击移除后确认，再发送原有的单项移除接口；取消或保存失败不移除食材。

上下滚动、短触碰、明显斜滑不触发左滑。管理模式保留原来的批量选择、修改分类和移除所选，此时不提供左滑，避免和勾选冲突。左滑仅修改原生微信小程序，网站冰箱继续使用原有按钮。

## 共用后台和数据

网站和小程序共用 wechat-gateway/domain/kitchen.ts 的规则。两人评分、公开结果、淘汰记录和自动选下一道在同一次厨房保存中完成。沿用带版本号的保存方式，冲突时重新读取最新记录再执行，两个实例同时完成评分也只会换一次。旧候选编号的迟到评分拒绝写入新菜。

普通查询、修改和备份导入响应都按登录身份隐藏未公开的分数。数据库保存完整分数；写操作使用原始记录，不能将返回给手机的隐藏内容写回数据库。partnerRated 是只用于返回的状态，不保存到记录中。历史里尚未完成双方评分的菜也继续隐藏对方分数。

新增可选字段：

- kitchen.mealPreferences：meatCount、vegCount，记录最近成功开始一轮的数量。
- meal.fridgeOnly：本轮是否只用冰箱食材。
- meal.rejected：淘汰候选编号、菜品编号、菜名、荤素和两人的最终分数。
- candidate.blocked：无法继续自动换菜时的中文原因。

这些字段存在原来的厨房内容里，无需新增表或修改SQL。旧数据没有新字段时仍能读取；旧晚餐本来没有保存食材限制，不能还原当时的选择，自动换菜默认不限制冰箱。已经出过结果的旧低分菜保留原结果，可手动换一道，或开始新一轮使用新规则。

开始搭配沿用 POST /api/kitchen，示例：

```json
{
  "action": "mealCreate",
  "meatCount": 2,
  "vegCount": 2,
  "fridge": true
}
```

score 接口保持原有参数；由第二个完成评分的请求触发后台自动换菜。replace 和 pick 沿用本轮食材限制和淘汰排除规则。冰箱左滑沿用 pantryRemove。

## 备份兼容

备份工具继续通过共同口令登录，但会分别选择两种身份，取两个人各自的分数合成完整备份。两次返回必须为同一版本，最多重新读取三次；持续变化时停止并提示。保存前移除只用于显示的 partnerRated，再执行原有格式和大小检查。普通页面不会因此拿到对方尚未公开的分数。

备份检查支持1～6道候选、新数量字段、淘汰记录和无法换菜说明，旧的一荤两素备份仍有效。导入完成后也用两份同版本读取结果合并并核对内容，避免把隐藏分数误认为丢失。
