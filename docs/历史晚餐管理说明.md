# 历史晚餐管理说明（旧版）

此文档保留早期实现记录。当前功能已改为独立“三餐日历”，取消历史复用，完成双人评分的菜品单独长期保存。以[三餐日历需求与方案](三餐日历需求与方案.md)为准。

## 已确认的用途

历史晚餐保存的是每轮选菜和评分结果，不代表这些菜已经实际做过或吃过。本次不增加“已吃完”的记录，也不根据评分推测实际饮食。

## 页面怎么用

1. 在“今晚吃什么”底部打开“历史晚餐”，按最新到最早查看每轮记录。
2. 卡片显示日期、荤素数量、菜名预览、入选数量和评分完成情况。日期沿用当时保存的值，旧记录没有具体时间，不补造时间。
3. 点击卡片或“查看菜品和评分”展开详情，一次展开一轮。详情显示当时的菜名、主要食材、入选结果和允许公开的评分。
4. 两个人没有都评完的菜，仍只显示本人分数和对方是否已评分；不会因为进入历史页就公开对方分数。
5. 搜索按历史菜名匹配，包含本轮淘汰菜的名称。淘汰结果按每次10条展开，继续点击可以查看更多。
6. 没有历史、没有搜索结果、没有入选菜、菜单中菜品失效，都分别给出说明。

“全部入选”指这轮保留的候选菜全部达到7分；“部分入选”指有入选菜，但其他菜未完成评分或低于7分；“未完成评分”指没有入选菜且仍有菜未评完；“未入选”指全部评完且没有达到7分的菜。

## 再吃这一顿

点击后先确认，成功后回到当前晚餐，开始新一轮评分。

- 只复用旧轮两个人都评完、合计大于等于7分的菜。旧轮有3道菜、只有2道入选，新轮就是这2道，不补随机菜。
- 后台根据菜品编号读取当前菜单，使用现在的菜名、食材和荤素分类；历史详情仍显示当时保存的内容。
- 新轮和每道候选菜都有新编号，分数全部清空。旧轮的评分和菜品内容不被改写。
- 按实际复用菜品的当前分类保存新的荤素数量。下一轮数量草稿在成功后更新为这一组数量。
- 菜品已删除或“不再推荐”，整次拒绝，提示重新选择，不偷偷换成另一道菜。
- 旧轮限定只用冰箱食材时，复用前还要检查现在的冰箱；缺食材则整次拒绝。没有保存限制的旧记录按不限冰箱处理，并明确显示旧记录未保存限制。
- 取消或保存失败，不开始新轮。小程序保存失败后需要重新同步成功，才允许继续操作。

当前正在评分的轮次不属于历史，不能用这项接口直接复制当前轮。开始新轮后，上一轮会进入历史。

## 保存与接口

沿用现有厨房数据，不增加数据库字段，不改备份格式。保留上限仍为最近30轮（包含当前轮），因此最多显示29轮历史；新轮可能移除超出上限的最早记录。单轮淘汰记录上限400条、厨房内容上限2MB仍生效。

网站和小程序共用历史文字整理方法。前端只发送历史轮编号，不提交要复制的评分或菜品内容：

```json
{"action":"mealRepeat","mealId":"历史轮编号"}
```

请求为 POST /api/kitchen。后台重新检查这轮是否仍存在、入选分数、当前菜单及冰箱。沿用厨房版本号保存：多实例同时修改时，保存发生冲突会读取最新内容重新校验，不覆盖另一人的已保存修改。整组校验完成才新增一轮，不产生只复制成功一半的晚餐。
