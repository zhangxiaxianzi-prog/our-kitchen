# 微信厨房后台迁移部署说明

这版直接读写MySQL，取代转发Sites接口的旧服务。先完成下面步骤，网站仍保留旧后台，不能直接把新空厨房当作原来的厨房。

## 1. 服务环境变量

在springboot-5wzu的服务设置中配置下列变量。数据库密码和登录密钥只放在微信控制台，不放进GitHub或压缩包。

| 变量 | 填写内容 |
| --- | --- |
| DB_HOST | 10.23.101.218 |
| DB_PORT | 3306 |
| DB_NAME | springboot_demo |
| DB_USER | root |
| DB_PASSWORD | 在控制台填写数据库密码 |
| KITCHEN_SESSION_SECRET | 新生成的固定随机密钥，至少32个字符 |
| WEB_ORIGINS | https://our-kitchen-oct09.berryokapi.chatgpt.site |
| PORT | 8080 |

服务在云端使用内网地址，数据库为MySQL 5.7。每个实例用相同密钥；修改密钥会影响原有登录和口令对应的厨房编号。不要在每次启动时重新生成。

可以在Mac终端执行下面命令生成密钥并复制到剪贴板，然后直接粘贴进控制台，不会在终端显示密钥：

```sh
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('hex'))" | pbcopy
```

## 2. 发布新后台

用户已授权助手提交本次厨房改动，并推送main触发现有CI/CD。用户自己修改的project.config.json仍留在本机，本次不包含；project.private.config.json是微信工具的个人配置，无须公开上传。新增domain、服务文件、package-lock.json都必须包含，不能只上传server.cjs。

GitHub仓库：zhangxiaxianzi-prog/our-kitchen，分支main，端口8080，目标目录wechat-gateway，Dockerfile选有、名称Dockerfile。环境变量需要在微信控制台配置；若尚未配置，新服务会停止启动，不能将自动构建成功当作服务可用。首次绑定、后续流水线是否真正运行，要看微信控制台发布结果。

如上传本次“微信厨房MySQL服务包.zip”，目标目录留空，Dockerfile在压缩包根目录。运行镜像安装锁定依赖并编译共用规则，不能用旧版只有两个文件的服务包。

启动时自动创建两个新表，不删除原来的表。缺少配置或连不上数据库会停止启动。健康检查建议填/ready，它会检查数据库；/health只代表进程可响应。

新服务地址：https://springboot-5wzu-325631-12-1311437624.sh.run.tcloudbase.com 。发布成功后访问该地址加/ready，应收到JSON：{"ok":true}。旧转发版本没有这个就绪检查接口。

## 3. 先验证独立测试厨房

微信开发者工具仍导入桌面“/Users/admin/Desktop/两人厨房”，AppID、环境和服务名不变。先用新的测试口令，两种身份分别登录，检查添加食材、三道菜、并发评分和采购入冰箱。两边2分和5分应显示7分入选。

可以在项目根目录运行下面检查，它会在新服务创建独立的随机测试厨房，不使用实际厨房记录：

```sh
KITCHEN_API_URL=https://springboot-5wzu-325631-12-1311437624.sh.run.tcloudbase.com node tests/网站小程序共享检查.mjs
```

此脚本验证云端HTTP接口与两个身份，不代表Sites页面已切换或微信真机验证完成。

## 4. 迁移原来的实际厨房

这一步期间，两个人先停止修改厨房。不要先在新后台用实际口令选菜或添加食材，否则为避免覆盖数据，导入会被拒绝。

在wechat-gateway目录运行：

```sh
node tools/厨房备份迁移.cjs 导出 /Users/admin/Desktop/原厨房.厨房备份.json
node tools/厨房备份迁移.cjs 导入 /Users/admin/Desktop/原厨房.厨房备份.json
```

两次均在本机输入同一个实际共同口令，输入过程不显示。导出保存菜单、冰箱、采购状态和30轮以内晚餐历史，不保存口令、票据或原厨房编号。文件只允许当前用户读写；已有同名文件不会被覆盖。不要将实际备份提交到公开仓库。

导入前验证结构和大小；只写入新建且版本为1的厨房。重传同一份备份不会回退后来新增的内容。导入工具比较新厨房内容和备份的摘要，只有一致才报告校验通过。若旧网站返回验证页，工具停止，不会把HTML保存为备份，也不会绕过验证；此时需要原平台导出实际数据，再继续迁移。

如果实际存在不止一个厨房，每个共同口令需要单独导出、导入。不能根据一个厨房的备份声称整个数据库已迁完。

## 5. 最后切换网站

确认实际厨房迁移一致后，将lib/厨房服务配置.json中的“启用微信后台”改为true，再构建并通过Sites重新发布原网站。网站将直接调用上述HTTPS服务，来源只允许原网站域名。新登录使用独立缓存项，需要重新输入共同口令。

当前Sites工具对原项目返回“找不到项目”，暂时不能重新发布。需要恢复原项目的工具访问后才能完成这一项，不能创建替代网站并当作原网站更新。

在网站与微信中分别修改食材、评分，另一边应读到结果。确认后恢复正常使用。旧网站记录保留用于回退，但切换后不能继续同时写旧后台。
