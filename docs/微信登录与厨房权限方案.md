# 微信登录与厨房权限方案

## 已确认范围与当前状态

2026年10月10日，用户确认新增微信账号登录、我的厨房、独立创建及申请加入、创建者审批、创建数量限制、白名单，以及独立管理员网页。用户明确不迁移旧厨房，暂不处理评分身份固定绑定，保留男生和女生自由选择。

本次代码已接入这些流程，尚未发布，也未联通真实MySQL或实际微信登录。不得将离线测试通过等同于线上可用。

## 微信登录和厨房访问

小程序用微信提供的临时登录凭证向后台请求账号登录。后台向微信固定接口核实身份，不信任小程序提交的账号标识，也不信任公网请求自报的微信身份头。微信AppSecret仅在云托管环境变量配置，不能放进小程序或GitHub。没有配置时服务可以启动，但微信登录会明确提示尚未配置。

账号票据与厨房票据分别保存。厨房票据带微信账号、厨房编号和评分身份，签名验证后还要查询厨房成员关系。账号票据不能用于厨房接口，厨房票据不能用于管理员网页。厨房票据和账号票据有效期30天，网页管理员会话有效期一小时。

我的厨房只返回当前微信账号已获准加入的厨房，每页20个，显示名称和最近访问时间。创建者能够处理加入申请。普通成员不能审批，也不能更换厨房口令。

创建厨房要明确填写名称并点击创建。加入口令由系统生成32字节随机内容，不采用用户填写的生日等口令。数据库只保存带服务密钥计算的口令查找值。创建成功后可复制口令，创建者之后也可以生成新口令；新口令使旧口令失效，已加入的成员不受影响。

输入不存在或格式错误的口令不会创建厨房，申请接口不返回厨房内容。非成员输入有效口令只产生申请，创建者同意后才能进入。普通用户和白名单用户都不能跳过审批。审批与成员登记在同一事务内保存，重复处理返回已变更提示。

原来的POST /api/login在生产入口返回410，旧票据不能访问新账号厨房。现有旧厨房数据不迁移或认领。本轮没有执行生产数据库删除；旧记录不会进入新账号列表，也不会通过旧票据读取。原口令登录方法仅留作旧业务规则离线回归，不再由生产入口提供。

## 名额及操作频率

普通账号每天最多创建一个厨房，同时最多拥有三个自己创建的厨房。受邀加入不占这三个名额。日期按北京时间计算。

账号创建计数和新厨房内容、创建者成员关系在一个事务内提交，使用账号版本检查，两个实例不能同时占用最后一个名额。不新增连表查询或显式行锁SQL。

白名单同时免除每日创建次数和拥有数量上限。白名单仍保留防止短时间大量请求的限制：每账号每15分钟最多20次创建操作、20次加入尝试。微信登录及加入操作还有共享的全局次数限制；所有实例共用数据库计数，不因扩容重新获得次数。这能限制单账号滥用，不能证明一个人只有一个微信账号。

## 白名单更新

正式名单保存MySQL。各实例按账号缓存结果60秒；缓存最多1000个账号，同账号并发查询合并。只在创建及必要的权限展示查询，不在每次冰箱刷新时查询。

管理修改先提交数据库及修改记录，再清除当前实例对应缓存。其他实例最多继续使用旧名单60秒。缓存过期后查询失败会拒绝本次创建，不沿用旧白名单权限。已通过权限检查的在途请求可能继续完成。用户明确接受新增和停用的60秒生效等待。

停用白名单不会删除账号已有厨房，仅对以后创建恢复普通限制。管理员权限与白名单权限分开，白名单不能管理名单或读取别人厨房。

## 管理员网页

管理员网页由同一后台提供，路径/admin。提供账号搜索、添加、启用和停用，名单和修改记录分页查看。不恢复原普通用户厨房网站。

页面生成两分钟有效的登录二维码，管理员在小程序中选择扫描登录管理网页，并确认自己正在使用的网页。后台验证账号属于可信管理员配置后批准。登录请求在数据库保存，各实例共用；二维码凭证与原浏览器私有凭证分开，只有原浏览器才能领取会话，且只能消费一次。

网页会话使用HttpOnly、Secure、SameSite=Strict Cookie，不把管理员票据交给小程序或保存在网页本地存储。修改接口校验网页来源，每次管理请求校验管理员权限。页面设置脚本来源和禁止嵌入策略，用户备注用文字节点显示。

首次管理员由KITCHEN_ADMIN_OPENIDS配置，不能让第一个登录者自动成为管理员。首次配置的管理员插入白名单；若该账号已在名单中或已停用，不因重启而覆盖。
