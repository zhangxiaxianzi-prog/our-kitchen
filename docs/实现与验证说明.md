# 实现与验证说明

## 项目结构

- app：页面、登录接口和厨房接口。
- lib：菜单、选菜评分规则和登录票据。
- db 与 drizzle：数据库表定义及发布迁移。
- docs：中文需求和使用说明。

## 数据保存

每个共同口令用服务端密钥计算厨房编号，数据库不保存口令原文。登录后发放带签名的票据，包含厨房编号、评分身份和30天有效期。厨房接口按票据读取对应数据，不接受页面指定其他厨房。

每个厨房保存一个有大小上限的数据记录。写入前读取版本，保存时比较版本；如果另一人先保存，重新读取最新记录再处理本次操作，最多重试8次。因此两个人同时打分不会用整页旧数据盖掉对方分数。候选菜有独立编号，换菜时更换编号，旧页面发来的评分会被拒绝。

服务器用一条数据库语句完成每次保存，不跨网络持有数据库锁，不依赖某台服务进程的内存。历史、食材、采购项和菜数均有上限。

## 运行密钥

KITCHEN_SESSION_SECRET 配置在 Sites 的运行环境中，源码和打包产物不包含线上值。桌面项目的 .dev.vars 只包含用于本地检查的假密钥，受忽略规则保护。

该密钥也参与厨房编号计算，必须长期保留。不要直接替换；如需更换，应先设计厨房数据迁移，否则旧口令将无法定位原厨房。

## 发布

用户已明确允许本次 Sites 发布所需的源代码提交、推送和打包。网站入口采用免 ChatGPT 登录访问，所有厨房数据接口仍要求有效登录票据。

## 验证结果

已通过类型检查和本地规则检查：7分入选、6分不入选、未评分等待、换菜重新评分、旧候选评分被拒绝、采购食材合并、菜单删除保留晚餐记录。

已通过本地真实接口检查：同口令共享、不同口令隔离、两个人同时评分和添加食材均保留双方操作，无登录、伪造票据和跨站写入被拒绝。

本地浏览器已检查登录页和晚餐候选页；发现手机缺少切换身份入口后已补充。线上发布及验证尚待完成。
